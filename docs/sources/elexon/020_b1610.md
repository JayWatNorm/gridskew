# B1610, Actual Generation Output Per Generation Unit

**Ingested.** `raw.elexon_b1610`, loaded by `gridskew_elexon_b1610_II` and
`..._SF`. Schedule, offsets and backfill are in
[021_b1610_ingestion.md](021_b1610_ingestion.md).

Every volume, run boundary and lag on this page is measured rather than taken
from the endpoint description — the script is `tests/adhoc/b1610_checks.py`.

## In plain terms

**The receipt.** What each power station actually generated in each half hour,
read off the meter.

Two things about it are awkward and both matter:

- It arrives **five days late**, because the metering has to be collected and
  reconciled first.
- The number **changes afterwards**. Settlement is re-run several times over
  the following months as better meter data arrives, and each run can revise
  the figure.

Compare this to `PN` (the promise) and the gap between them is a shortfall: a
station that said it would produce and did not.

---

Actual metered volume in MWh per settlement period per BM unit. The outturn
side of the thesis: what a generator actually produced, against `PN`'s record of
what it said it would.

Elexon's own description is worth quoting, because it answers two design
questions at once:

> The information is published **five days after the end of the operational
> period** based on the **Interim Information (II) Settlement Run**, and the
> data is **refreshed by subsequent Settlement Runs**.
>
> The generation output returned by this endpoint is the **metered volume and
> not the instantaneous power output** as often appears in other
> specifications.

## Endpoint

```
GET https://data.elexon.co.uk/bmrs/api/v1/datasets/B1610/stream
```

| Parameter | Required | Notes |
|---|---|---|
| `from` | yes | ISO datetime |
| `to` | yes | ISO datetime |
| `settlementRunType` | no | Free-text string, no enumerated values. **Omitting does not get you all runs** — it returns whichever run is currently in force. See below |
| `settlementPeriodFrom` | no | **Did not filter when tested.** See below |
| `settlementPeriodTo` | no | **Did not filter when tested.** See below |
| `bmUnit` | no | Array. Not used in ingestion; pull everything |

## Response

Bare array, no envelope.

```json
[
  {
    "dataset": "B1610",
    "psrType": "Generation",
    "bmUnit": "T_DRAXX-1",
    "nationalGridBmUnitId": "DRAXX-1",
    "settlementDate": "2026-08-01",
    "settlementPeriod": 3,
    "halfHourEndTime": "2026-08-01T00:30:00",
    "settlementRunType": "II",
    "quantity": 0.000
  }
]
```

| Field | Type | Notes |
|---|---|---|
| `dataset` | `str` | Always `B1610` |
| `psrType` | `str` | e.g. `Generation` |
| `bmUnit` | `str` | Elexon identifier. **Never null** — measured across a market-wide day |
| `nationalGridBmUnitId` | `str` | National Grid identifier. **Null on 71.8% of rows.** Note the `Id` suffix, which `PN` and `QPN` do not have |
| `settlementDate` | `str` | **Local time date** |
| `settlementPeriod` | `int` | 1 to 50 |
| `halfHourEndTime` | `str` | **Naive, no timezone suffix.** Attach UTC after parsing |
| `settlementRunType` | `str` | Which settlement run produced this value |
| `quantity` | `float` | MWh. Can be positive, negative or zero |

## Settlement runs and restatement

The same period is republished as settlement progresses, with a different
`settlementRunType` and potentially a different `quantity`.

**Measured 2026-08-23** across 42 one-hour windows from 7 to 720 days old:

| Run | Live from | Live until |
|---|---|---|
| `II` | **7 days** | ~21 |
| `SF` | ~28 | ~42 |
| `R1` | ~49 | ~112 |
| `R2` | ~119 | ~210 |
| `R3` | ~225 | ~390 |
| `RF` | **~420** | 720+ |

**`RF` lands at about fourteen months**, not the seven the published timescales
imply. The R3/RF boundary sits between 390 and 420 days.

**Run type is per unit-period, not per settlement day.** A day 112 days old
returned `{'R1': 26,484, 'II': 12}`, and one at 300 days returned
`{'R3': 23,169, 'II': 3}`. A handful of unit-periods never progress past the
interim run. Any downstream model that filters run type at the day level is
wrong; it has to resolve per `(bm_unit, settlement_date, settlement_period)`.

**Publication is on working days, not calendar days.** Settlement day Saturday
16 August plus five working days is Friday the 22nd, visible at seven calendar
days — exactly as measured. Around bank holidays the same rule stretches: a
settlement day of 24 December 2025 would not publish until about 5 January,
**twelve calendar days**. A poller on a fixed calendar offset will find nothing
for those days.

## Superseded runs are discarded, and cannot be recovered

**The single most important finding about this dataset.**

`settlementRunType` works as a *request* parameter — asking for different runs
returns different results, so it is not being ignored. Which makes this result
conclusive, for settlement day 2025-10-27 measured at 300 days old:

| Requested run | Rows returned |
|---|---|
| `II` | 3 — the stragglers above |
| `SF` | **0** |
| `R1` | **0** |
| `R2` | **0** |
| `R3` | 23,169 — current |
| `RF` | **0** |

SF, R1 and R2 all existed for that day. **They are gone.** Elexon serves only
the run currently in force for each unit-period and discards what it supersedes.

Three consequences:

1. **An earlier run cannot be fetched retrospectively.** Whatever `II` said for
   a settlement day is unrecoverable once `SF` replaces it.
2. **Restatement can only be captured forwards**, by polling while each run is
   live. This is the same mechanism as the Carbon Intensity forecast, which
   overwrites its stored value in place — see the project README. The record of
   how a metered volume was revised exists nowhere public.
3. **"How much does II move?" cannot be answered from history.** It requires
   archiving `II` now and comparing against a later run. The II to SF transition
   happens between days 21 and 28, so **the first measurement is available three
   weeks after ingestion starts** rather than fourteen months.

**This constrains the A6 design.** "Keep first and latest" preserves restatement
magnitude only for runs polled while they were live — magnitude is not something
the source can be asked for retrospectively.

## Table

The key must include the run type, since the same period is republished once per
run. **`retrieved_at` is deliberately not in it** — B1610 labels its own
revisions, so a re-poll finding nothing new inserts nothing:

```sql
PRIMARY KEY (bm_unit, settlement_date, settlement_period, settlement_run_type)
```

> **This is the mirror image of the PN key, and generalising from PN would break
> it.** PN keys on `national_grid_bm_unit` because `bmUnit` is null on 1.4% of
> rows. **B1610 is inverted**: `bmUnit` is never null, and
> `nationalGridBmUnitId` is null on **71.8%** of rows.
>
> `sql/init/005_elexon_b1610.sql` was written with the PN pattern applied —
> `national_grid_bm_unit_id text NOT NULL` and that column leading the key. On a
> market-wide day that is **303,094 not-null violations**, and it would fail part
> way through the first insert rather than at deploy time.
>
> `national_grid_bm_unit_id` must be **nullable**, and `bm_unit` must be
> `NOT NULL` and lead the key.

**Uniqueness within a poll is confirmed by arithmetic**, not assumed:

```
2,588 units with an NG id  x  46 periods  =  119,048
6,589 units without        x  46 periods  =  303,094
9,177 units total          x  46 periods  =  422,142   exact
```

Every unit files exactly one row per period per settlement run, so no unit-period
appears twice within a single fetch.

`quantity` is `numeric`, not `float`. **Measured: exactly three decimal places on
every row.** Parsed through `json.loads(..., parse_float=Decimal)` so the value
never touches binary floating point — these get summed across millions of rows,
and float error accumulates in exactly that operation.

## Volume — the earlier estimate was 22x low

**Loaded to dev 2026-08-23** with the real poller, one UTC-day window at the
14-day offset:

| | |
|---|---|
| Rows fetched per run | **449,673** — 9,177 units x 49 periods |
| Rows stored per settlement day | **440,496** — 48 periods |
| Duplicated per run | 9,177 — one period, absorbed by `ON CONFLICT` |
| Distinct units | **9,177** |
| — with a National Grid id | 2,588 |
| — Elexon identifier only | **6,589** |
| Null `bm_unit` | **0** — the key holds |
| Null `national_grid_bm_unit_id` | 71.8% |
| `quantity` range | −658.300 to 699.850 MWh |

> **A day window returns 46 periods at a 7-day offset and 49 at 14.** At seven
> days the *next* settlement day is only six days old and therefore unpublished,
> so its periods 1 and 2 are absent. Measure volumes at the offset you intend to
> poll at, or the figure is a property of the probe rather than of the data.

**B1610 is the largest table in the project, not the smallest.** It is bigger
than PN because it meters **embedded and secondary units that never file a PN** —
9,177 against PN's 2,552. Those 6,589 Elexon-only units are the difference, and
they are why the identifier pattern is inverted.

**Restatement multiplies this.** Unlike PN, where restatement is an open
question, B1610 restates by design across six settlement runs. Re-polling all of
them would approach **160 GB/year**. That is now the dominant storage decision in
the project and needs settling before the poller is written, not after.

## The lag is seven days, not five

Elexon's description says five days after the operational period. **Measured
2026-08-23, it is seven, and the boundary is a hard cliff rather than a ramp:**

| Days back | Rows in a 1h window |
|---|---|
| 1 to 6 | **0** |
| 7 to 10 | 27,531 |

Build against seven, and treat Elexon's "five" as a floor rather than a figure.

**The lag and the BST offset interact.** A UTC-day request for 2026-08-16
returned 46 settlement periods, not 48 — periods 1 and 2 of settlement day 17
fall inside that UTC window, but settlement day 17 was only six days old and
therefore unpublished. A DAG whose window is not offset past the lag returns an
empty array and writes nothing.

## Traps

**`halfHourEndTime` is naive** where PN's `timeFrom` carries `Z`. Two datasets
from the same API with different timestamp conventions.

**`settlementDate` is local time**, so it can differ from the UTC date of
`halfHourEndTime`. Derive one from the other and you will be wrong for an hour
of every summer day.

**Ingestion never passes `settlementRunType`, and "get all runs" is not on
offer.** The endpoint description implies otherwise, so the actual behaviour is
worth stating plainly — it is counter-intuitive:

- The API holds **one run per unit-period**, the one currently in force.
- Omitting the parameter returns that run. It does not return a history.
- Passing a *superseded* run returns **zero rows** — measured, see above.

So **the poll offset is the run-type selector.** You do not choose which run you
receive by parameter; you choose it by how long you wait before asking:

| Poll at | Returns |
|---|---|
| 14 days | `II` |
| 35 days | `SF` |
| 80 days | `R1` |
| 165 days | `R2` |
| 300 days | `R3` |
| 450 days | `RF` |

That is why this project runs two DAGs at fixed offsets rather than one job with
a parameter, and why a missed poll cannot be made up later.

**`settlementPeriodFrom` and `settlementPeriodTo` did not filter.** Passing 1
and 1 across a 61 day window returned all 48 periods per day.

BOALF and MELS document these parameters as switching `from` and `to` to filter
on settlement date rather than time. **B1610's description carries no such
paragraph**, and the behaviour was not observed. Do not use them here without
retesting.

**The boundary is inclusive at both ends.** A one-hour request returned 27,531
rows — 9,177 units across **three** periods, not two. A UTC-day request returns
**49** periods: the period containing `from` and the period containing `to` are
both included.

That produces clean coverage across consecutive daily runs:

```
each settlement day:  periods 1, 2   from the PREVIOUS run - they end before 00:00Z
                      periods 3-48   from its own run
                      period 3       arrives in both, ~9,177 duplicate rows per run
```

No gaps, and the overlap is absorbed by `ON CONFLICT DO NOTHING`. **This is the
concrete payoff for taking `retrieved_at` out of the key** — with it in, that
daily overlap would store 3.3M redundant rows a year instead of none.

**Verified in dev, 2026-08-23**: the same window loaded twice left the row count
unchanged. Re-polling is idempotent, which is what the two-rung design depends
on — the SF poll must supersede rather than duplicate.

**`settlementDate` is confirmed local time — and only period 1 ever disagrees.**
Measured across a settlement-day boundary, 82,593 rows: **9,177 mismatches, all
of them period 1.**

Period 2 agrees because `halfHourEndTime` is the period *end* — period 2 ends at
00:00Z on the settlement date itself. Only period 1, ending at 23:30Z the
previous day, falls on the other side.

> **Check this across a settlement-day boundary, not inside one.** A window built
> as `[day_start, day_start + 1 day]` excludes period 1 by construction, so no
> mismatch can appear however the parse behaves.

**No documented maximum range.** A 92 day request returned the full span with
no truncation. Note that 92 days is the documented cap for `NDFD` and `TSDFD`,
so it may be a platform default rather than an absence of limit. Chunking by
day sidesteps the question and keeps responses manageable anyway.
