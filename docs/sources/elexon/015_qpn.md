# QPN, Quiescent Physical Notifications

**Ingested.** `raw.elexon_qpn`, loaded daily by `gridskew_elexon_qpn` alongside
`PN`. Schedule, chunking and backfill are in
[016_qpn_ingestion.md](016_qpn_ingestion.md).

## In plain terms

**An optional MW profile for an underlying process within a BM Unit.**

QPN is a physical quantity, not a monetary cost. It declares the generation or
demand expected from an underlying process that forms part of the BM Unit's
operation. Submission is optional, and many units submit rows of zero.

Where `MELS` declares the headroom a unit *could* reach and `PN` declares what it
*intends* to do, QPN declares an internal quantity that is netted off the PN for
one specific purpose, described below.

---

## What it is for, and the limits of that

Two sources say different-sized things, and the difference matters.

The [**endpoint description**](https://bmrs.elexon.co.uk/api-documentation/endpoint/datasets/QPN/stream)
says:

> Quiescent Physical Notifications describe the MW levels to be deducted from
> the Physical Notification of a BM Unit to determine a resultant operating
> level.

The [**BSC glossary**](https://www.elexon.co.uk/bsc/glossary/quiescent-physical-notification/)
is narrower and more precise:

> A series of MW values and associated times expressing the volume of generation
> or demand expected to be generated or consumed by an underlying process that
> forms part of the operation of a particular BM Unit.
>
> QPN values are **not used in Settlement**, but if submitted to the System
> Operator are deducted from Physical Notifications to determine a net operating
> level **to which the Dynamic Data of a BM Unit apply**.
>
> Submission of QPNs is **optional**.

Three things follow that the endpoint description alone would not tell you:

1. The deduction exists to establish the level **the Dynamic Data apply to** —
   ramp rates, stable limits, minimum zero times. It is not stated to be a
   general restatement of the unit's commitment.
2. **QPN is not used in Settlement.** `B1610` is settlement metered volume. So
   subtracting a non-settlement quantity from a settlement comparison is not
   self-evidently correct.
3. It is **optional**, so an absent row does not mean zero deduction.

## Open question: does QPN belong in the shortfall?

**Unresolved, and it should not be assumed either way.**

`shortfall = (PN - QPN) - B1610` looks obvious from the endpoint description's
"resultant operating level", and it is the reading to be careful of: the BSC
glossary scopes that level to Dynamic Data and rules QPN out of Settlement
entirely.

The formal subtraction is not in dispute. The unresolved project choice is
whether that Dynamic Data operating level is the correct comparator for B1610
metered output. For units with a non-zero QPN, compare metered output against
both candidates after PN and QPN have been aligned to common segment boundaries
and integrated to settlement-period MWh. Resolve repeated polls and choose the
required B1610 settlement run before comparing values.

The comparison measures the practical effect, but the final choice must also
match the documented definition of shortfall. Record that decision before the
S8 intermediate models depend on one interpretation.

## Endpoint

```
GET https://data.elexon.co.uk/bmrs/api/v1/datasets/QPN/stream
```

| Parameter | Required | Notes |
|---|---|---|

| `to` | yes | ISO datetime |

| `settlementPeriodTo` | no | As above |

Identical to `PN`. No documented maximum range.

## Response

Bare array, no envelope. **The spec defines `QPN` and `PN` against the same
schema object** — `PhysicalNotificationData` — so the field list is not merely
similar, it is the same one:

| Field | Type | Notes |
|---|---|---|
| `dataset` | `str` | `QPN`. The only field that distinguishes the two responses |
| `settlementDate` | `str` | **Local time date.** See the source README |
| `settlementPeriod` | `int` | 1 to 50 |
| `timeFrom` | `str` | UTC, `Z` suffix |
| `timeTo` | `str` | UTC |
| `levelFrom` | `int` | MW to deduct at `timeFrom` |
| `levelTo` | `int` | MW to deduct at `timeTo` |
| `nationalGridBmUnit` | `str` | |
| `bmUnit` | `str` | |

**Confirmed live 2026-08-20, fixture recaptured 2026-08-22** — see
`tests/fixtures/elexon/qpn_stream.json`. The first check, one hour for
`T_DRAXX-1`, returned the exact field list above, bare array, descending period
order, boundary periods included at both ends — all identical to PN's observed
behaviour. The committed fixture is now a **24-row composite across five units**,
deliberately the same units and windows as `pn_stream.json` so the two are
directly comparable.

## QPN is a ramp too — but not the same ramp

`levelFrom` and `levelTo` describe a line between two instants, exactly as they
do for `PN`, and the format permits several point pairs inside one period.

**Measured 2026-08-22: QPN's segment boundaries are independent of PN's.** Same
units, same windows:

| Unit and window | PN | QPN |
|---|---|---|
| `T_DRAXX-1`, SP29–30 | **4 rows** — 1, 11, 19, 29 minutes | **2 rows** — 30, 30 |
| `T_ABRBO-1`, one hour | **6 rows**, 15-minute segments | **4 rows**, 30-minute |

Where PN split a period four ways during a start-up ramp, QPN filed two plain
half-hour rows. Both fixtures are committed and comparable —
`pn_stream.json` and `qpn_stream.json` cover the same units and windows
deliberately.

**So `PN - QPN` cannot be a row-to-row join.** They are two piecewise-linear
functions with different breakpoints. Subtracting them means overlaying both
onto a common set of boundaries — the union of each side's segment edges — and
only then integrating.

That is strictly harder than the planned PN-against-B1610 integration, and it
is a second reason to settle the open question below before building anything
that depends on the deduction.

## How common is it

Volumes, chunking and the backfill approach are in
[016_qpn_ingestion.md](016_qpn_ingestion.md).

### Counted across a full year — QPN is almost never non-zero

41,533,137 rows, 2025-08-22 to 2026-08-23, every unit:

| | |
|---|---|
| Total rows | **41,533,137** |
| Non-zero rows | **18,300** — 0.044% |
| Units with any non-zero QPN | **1** |
| Null `bmUnit` | 657,743 — **identical to PN, to the row** |
| Null `nationalGridBmUnit` | **0** — confirms the key |

The single unit is **`T_WILCT-1`**, at a constant **−60 MW**.

18,300 non-zero rows over 366 runs is **exactly 50 per run, every run, with zero
variance.** Not approximately fifty — fifty, for a year, without a gap or an
exception. And 50 rather than 48 is itself a confirmation: it is 48 settlement
periods plus the two boundary periods a UTC-aligned window picks up from the next
settlement day.

In the measured archive, the value behaves like a fixed registered value rather
than a varying operational series. This observation does not establish the
underlying process or its cost.

**This bounds the open question rather than answering it.** Whether `PN − QPN` is
the right promise affects **one BM unit in the market**. Every other unit's
shortfall figures are identical under either reading, so nothing downstream is
blocked.

QPN is about **10% smaller than PN** (41.5M against 46.2M rows), and **123 units
file a PN and never a QPN** — the optional submission from the glossary, visible
in the data.

### The one unit with non-zero QPN

From `/reference/bmunits/all`, 2026-08-23:

| | |
|---|---|
| `bmUnitName` | **ETOL - Wilton Site** |
| `leadPartyName` | **SembCorp Utilities (UK) Ltd** |
| `fuelType` | `BIOMASS` |
| `bmUnitType` | `T` — transmission connected |
| `generationCapacity` | **182.000** |
| `demandCapacity` | **−120.000** |
| `workingDayCreditAssessmentExportCapability` | **72.800** |
| `workingDayCreditAssessmentImportCapability` | **−48.000** |

The registry identifies it as a transmission-connected biomass unit with both
generation and demand capacity. That is consistent with the BSC definition of
QPN as an underlying process quantity, but the registry and PN values do not
measure the site's internal consumption. No site-load figure is inferred from
them.

### PN and QPN behave differently

Distribution of `T_WILCT-1`'s PN across the year, top values:

```
+32 MW  3,293 rows      -32 MW  1,097 rows
+12 MW  1,935 rows       -8 MW    842 rows
+35 MW    736 rows      -14 MW    324 rows
  0 MW    405 rows      -30 MW    311 rows
```

**The PN swings from −32 to +37 MW. The QPN does not move at all.** Roughly two
exports for every import, rarely idle, and — across the whole year — **every row
has `level_from = level_to`.** It steps between flat levels rather than ramping,
which is a useful contrast to Drax's minute-level start-up segments.

QPN is therefore a fixed offset applied to a varying PN for this unit. That
observation confirms the two series are independent quantities; it does not by
itself decide whether the settlement shortfall should use PN or PN minus QPN.
The registry's credit-assessment fields are financial-cover calculations, not
operational limits, so they are not used to resolve the question.

### `B1610` makes the effect measurable

For a settled day, compare `T_WILCT-1` metered output against both candidates.
**The candidate ranges do not overlap**, so the measurement should distinguish
their practical effect:

```
raw PN      -32 ... +37
PN - QPN    +28 ... +97
```

A single unit and a single query, rather than a fleet-wide analysis. Both
fixtures contain this unit for the same window, so the case is reproducible
without an API call.

---

**Units submit QPN rows of zero.** All four captured Drax rows carry `levelFrom`
and `levelTo` of 0, so a QPN row exists even when there is nothing to deduct.
Three consequences:

- Most of the per-period volume is zero rows. **Counted across a full year:
  99.96% of them.**
- Submission is **optional** per the BSC glossary, so a missing row means
  "this unit does not submit QPN", not "the deduction is zero". Those are
  different things in a join, and only an outer join is safe.
- A table full of zeros is not evidence of a broken poller. The table comment
  documents this expected sparsity.

## Table

`raw.elexon_qpn`, built by `sql/init/004_elexon_qpn.sql`. Same shape as the `PN`
table, same key, because the grain is identical:

```sql
PRIMARY KEY (national_grid_bm_unit, time_from, retrieved_at)
```

**Keyed on the National Grid identifier, not the Elexon one.** Counted across a
full year, this table has **657,743 null `bmUnit` rows and zero null
`nationalGridBmUnit` rows**. `raw.elexon_pn` has **exactly 657,743 too** — the
same number to the row, so the National Grid identifier is the stable key in
both datasets. See [010_pn.md](010_pn.md).

`bm_unit` is nullable. `settlement_date` and `settlement_period` are columns but
not key parts: both are derived from `time_from`, which is an absolute instant, so
they add index bytes without adding a guarantee.

Kept as its own table rather than columns on the `PN` table. The raw layer
records what each source published, and these are two publications that can
arrive at different times and be revised independently. Combining them is a
staging-layer decision — and given the open question above, one that should be
made explicitly rather than baked into ingestion.

## Two modules, not one

`PN` and `QPN` share an OpenAPI schema object, identical parameters and identical
grain, which is the strongest case in the Elexon set for a single parameterised
parser.

They are implemented as separate modules so each ingestion path remains readable
and can diverge safely if the source schemas change. Paired fixtures and tests
check that their shared fields continue to behave consistently.
