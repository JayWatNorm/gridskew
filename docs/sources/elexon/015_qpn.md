# QPN, Quiescent Physical Notifications

**Not yet ingested.** Planned for Phase 1, alongside `PN`.

## In plain terms

**A house-keeping process running inside the station.**

Quiescent means at rest. A QPN declares MW being generated or consumed by
something that is part of how the unit operates, rather than by the unit's
dispatchable output. It is optional, and many units submit rows of zero.

Where `MELS` declares the headroom a unit *could* reach and `PN` declares what it
*intends* to do, QPN declares an internal quantity that is netted off the PN for
one specific purpose, described below.

---

## What it is for, and the limits of that

Two sources say different-sized things, and the difference matters.

The **endpoint description** says:

> Quiescent Physical Notifications describe the MW levels to be deducted from
> the Physical Notification of a BM Unit to determine a resultant operating
> level.

The **BSC glossary** is narrower and more precise:

> A series of MW values and associated times expressing the volume of generation
> or demand expected to be generated or consumed by an underlying process that
> forms part of the operation of a particular BM Unit.
>
> QPN values are **not used in Settlement**, but if submitted to the System
> Operator are deducted from Physical Notifications to determine a net operating
> level **to which the Dynamic Data of a BM Unit apply**.
>
> Submission of QPNs is **optional**.

Three things follow that the endpoint description alone would not tell you:

1. The deduction exists to establish the level **the Dynamic Data apply to** —
   ramp rates, stable limits, minimum zero times. It is not stated to be a
   general restatement of the unit's commitment.
2. **QPN is not used in Settlement.** `B1610` is settlement metered volume. So
   subtracting a non-settlement quantity from a settlement comparison is not
   self-evidently correct.
3. It is **optional**, so an absent row does not mean zero deduction.

## Open question: does QPN belong in the shortfall?

**Unresolved, and it should not be assumed either way.**

An earlier version of this page asserted `shortfall = (PN - QPN) - B1610` as
settled. It was not. That claim came from reading "resultant operating level" in
the endpoint description as *the* operating level, when the glossary scopes it to
Dynamic Data and rules QPN out of Settlement entirely.

This is an **empirical question the pipeline can answer** once data exists. For
units with a non-zero QPN, compare metered output against both candidates:

```sql
SELECT p.bm_unit, p.settlement_date, p.settlement_period,
       p.level_from AS pn, q.level_from AS qpn, b.quantity AS metered
FROM raw.elexon_pn p
JOIN raw.elexon_qpn q USING (bm_unit, time_from)
JOIN raw.elexon_b1610 b ON b.bm_unit = p.bm_unit
                       AND b.settlement_date = p.settlement_date
                       AND b.settlement_period = p.settlement_period
WHERE q.level_from <> 0;
```

Whichever of `pn` or `pn - qpn` tracks `metered` more closely is the answer, and
it is a result rather than a reading. Settle it before the S8 intermediate models
depend on one interpretation.

## Endpoint

```
GET https://data.elexon.co.uk/bmrs/api/v1/datasets/QPN/stream
```

| Parameter | Required | Notes |
|---|---|---|
| `from` | yes | ISO datetime |
| `to` | yes | ISO datetime |
| `settlementPeriodFrom` | no | Untested on this dataset, as with `PN` |
| `settlementPeriodTo` | no | As above |
| `bmUnit` | no | Array. Not used in ingestion; pull everything |

Identical to `PN`. No documented maximum range.

## Response

Bare array, no envelope. **The spec defines `QPN` and `PN` against the same
schema object** — `PhysicalNotificationData` — so the field list is not merely
similar, it is the same one:

| Field | Type | Notes |
|---|---|---|
| `dataset` | `str` | `QPN`. The only field that distinguishes the two responses |
| `settlementDate` | `str` | **Local time date.** See the source README |
| `settlementPeriod` | `int` | 1 to 50 |
| `timeFrom` | `str` | UTC, `Z` suffix |
| `timeTo` | `str` | UTC |
| `levelFrom` | `int` | MW to deduct at `timeFrom` |
| `levelTo` | `int` | MW to deduct at `timeTo` |
| `nationalGridBmUnit` | `str` | |
| `bmUnit` | `str` | |

**Confirmed live 2026-08-20** — see `tests/fixtures/elexon/qpn_stream.json`.
One hour for `T_DRAXX-1` returned the exact field list above, bare array,
descending period order, boundary periods included at both ends — all identical
to PN's observed behaviour.

## QPN is a ramp too — but not the same ramp

`levelFrom` and `levelTo` describe a line between two instants, exactly as they
do for `PN`, and the format permits several point pairs inside one period.

**Measured 2026-08-22: QPN's segment boundaries are independent of PN's.** Same
units, same windows:

| Unit and window | PN | QPN |
|---|---|---|
| `T_DRAXX-1`, SP29–30 | **4 rows** — 1, 11, 19, 29 minutes | **2 rows** — 30, 30 |
| `T_ABRBO-1`, one hour | **6 rows**, 15-minute segments | **4 rows**, 30-minute |

Where PN split a period four ways during a start-up ramp, QPN filed two plain
half-hour rows. Both fixtures are committed and comparable —
`pn_stream.json` and `qpn_stream.json` cover the same units and windows
deliberately.

**So `PN - QPN` cannot be a row-to-row join.** They are two piecewise-linear
functions with different breakpoints. Subtracting them means overlaying both
onto a common set of boundaries — the union of each side's segment edges — and
only then integrating.

That is strictly harder than the PN-against-B1610 integration the S2 macro
already has to do, and it is a second reason to settle the open question below
before building anything that depends on the deduction.

## How common is it

**An earlier estimate of ~250 rows per settlement period on this page was wrong
by a factor of ten.** It was inferred from the byte size of a response that had
been truncated by the measuring tool, not by the API, and presented as if it were
a count.

PN, which shares this schema, measures at **~2,700 rows per settlement period**
and **~130,000 per day** market-wide. QPN is assumed to be the same order until
counted directly. Volumes, chunking and the backfill approach are in
[016_qpn_ingestion.md](016_qpn_ingestion.md).

### Counted market-wide, 2026-08-22 — QPN is almost never non-zero

One full day, every unit:

| | |
|---|---|
| Total rows | **119,600** |
| Non-zero rows | **50** — 0.04% |
| Units with any non-zero QPN | **1** |
| Null `bmUnit` | 2,450 — the same 49 units as PN |
| Null `nationalGridBmUnit` | **0** — confirms the key |

The single unit is **`T_WILCT-1`**, at a constant **−60 MW** across all 48
periods.

**This nearly settles the open question by making it almost irrelevant.**
Whether `PN − QPN` is the right promise affects **one BM unit in the market**.
Whatever the answer, the shortfall figures for every other unit are unchanged.

QPN is also **13,000 rows a day smaller than PN** (119,600 against 132,728),
consistent with submission being optional.

### The one unit is the whole question in a single row

Same unit, same period, 2026-08-21:

```
PN   = -14 MW        (importing)
QPN  = -60 MW
PN - QPN = +46 MW    (exporting)
```

**Applying the deduction flips the sign.** Either this unit imported 14 MW or it
exported 46 MW, and the two readings are not close.

**`B1610` settles it directly.** Once metered output for `T_WILCT-1` is
available for a settled day, compare it against both candidates — the one it
matches is the right interpretation. That is the pre-registered test in a form
that needs a single unit and a single query, rather than a fleet-wide analysis.

Both fixtures now contain this unit for the same window, so the case is
reproducible without an API call.

---

**Units submit QPN rows of zero.** All four captured Drax rows carry `levelFrom`
and `levelTo` of 0, so a QPN row exists even when there is nothing to deduct.
Three consequences:

- Much of the per-period volume above is likely zero rows, so how often QPN is
  *non-zero* remains unknown. One aggregate query during S1.1 settles it.
- Submission is **optional** per the BSC glossary, so a missing row means
  "this unit does not submit QPN", not "the deduction is zero". Those are
  different things in a join, and only an outer join is safe.
- A table full of zeros is not a broken poller. Worth saying so in the table
  comment, because someone will assume otherwise.

## Proposed table

Same shape as the `PN` table, same key, because the grain is identical:

```sql
PRIMARY KEY (national_grid_bm_unit, time_from, retrieved_at)
```

**Keyed on the National Grid identifier, not the Elexon one.** PN — which shares
this schema — has a null `bmUnit` on 1.8% of rows and never a null
`nationalGridBmUnit`. QPN is submitted by the same units, so the same is assumed
until counted. See [010_pn.md](010_pn.md).

`bm_unit` is nullable. `settlement_date` and `settlement_period` are columns but
not key parts: both are derived from `time_from`, which is an absolute instant, so
they add index bytes without adding a guarantee.

Kept as its own table rather than columns on the `PN` table. The raw layer
records what each source published, and these are two publications that can
arrive at different times and be revised independently. Combining them is a
staging-layer decision — and given the open question above, one that should be
made explicitly rather than baked into ingestion.

## Two modules, not one

`PN` and `QPN` share an OpenAPI schema object, identical parameters and identical
grain, which is the strongest case in the Elexon set for a single parameterised
parser.

**Built as two separate modules regardless**, decided 2026-08-21: each file is
readable start to finish with no indirection, and if the two datasets diverge
nothing needs untangling. The cost, accepted knowingly, is that a parse bug has
to be fixed twice.

## Priority

**Phase 1, first — same session as `PN`.** Not because the deduction is known to
be required, but because it is cheap to ingest alongside PN and the open question
above cannot be answered without the data. Ingesting it keeps the option open;
skipping it forecloses the analysis.
