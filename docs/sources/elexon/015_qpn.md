# QPN, Quiescent Physical Notifications

**Not yet ingested.** Planned for Phase 1, alongside `PN`.

## In plain terms

**The part of the promise that does not count.**

A unit's Physical Notification says how much it intends to produce. A Quiescent
Physical Notification says how much of that figure to **take back off again** to
get the level the unit is actually expected to run at.

```
resultant operating level  =  PN  -  QPN
```

So a station with a PN of 300 MW and a QPN of 50 MW is expected to deliver
250 MW, not 300 MW.

**This is why it matters here.** The whole project starts from
`shortfall = promised - delivered`. Take `PN` as the promise and every unit with
a non-zero `QPN` looks like it fell short by the quiescent amount, every
settlement period, whether or not anything went wrong. The shortfall would be
real in the arithmetic and imaginary in the world.

---

From the endpoint description:

> Quiescent Physical Notifications describe the MW levels to be deducted from
> the Physical Notification of a BM Unit to determine a resultant operating
> level.

## Endpoint

```
GET https://data.elexon.co.uk/bmrs/api/v1/datasets/QPN/stream
```

| Parameter | Required | Notes |
|---|---|---|
| `from` | yes | ISO datetime |
| `to` | yes | ISO datetime |
| `settlementPeriodFrom` | no | Untested on this dataset, as with `PN` |
| `settlementPeriodTo` | no | As above |
| `bmUnit` | no | Array. Not used in ingestion; pull everything |

Identical to `PN`. No documented maximum range.

## Response

Bare array, no envelope. **The spec defines `QPN` and `PN` against the same
schema object** — `PhysicalNotificationData` — so the field list is not merely
similar, it is the same one:

| Field | Type | Notes |
|---|---|---|
| `dataset` | `str` | `QPN`. The only field that distinguishes the two responses |
| `settlementDate` | `str` | **Local time date.** See the source README |
| `settlementPeriod` | `int` | 1 to 50 |
| `timeFrom` | `str` | UTC, `Z` suffix |
| `timeTo` | `str` | UTC |
| `levelFrom` | `int` | MW to deduct at `timeFrom` |
| `levelTo` | `int` | MW to deduct at `timeTo` |
| `nationalGridBmUnit` | `str` | |
| `bmUnit` | `str` | |

**Confirmed live 2026-08-20** — see `tests/fixtures/elexon/qpn_stream.json`.
One hour for `T_DRAXX-1` returned the exact field list above, bare array,
descending period order, boundary periods included at both ends — all identical
to PN's observed behaviour.

## QPN is a ramp too

`levelFrom` and `levelTo` describe a line between two instants, exactly as they
do for `PN`. A unit can submit several point pairs inside one settlement period.

**So the deduction is not a scalar.** Subtracting QPN from PN means aligning two
ramps that may have different point pairs within the same period, then
integrating the difference. That is the same problem the settlement period macro
at S2 already has to solve for PN against B1610, and it should be solved once.

## How common is it

A single settlement period returned roughly 69 KB from this endpoint. Against
the observed row size in `tests/fixtures/elexon/pn_stream.json`, about 272 bytes
per row, that implies on the order of **250 rows for one half hour**.

**This is an estimate from response size, not a counted figure** — the response
was too large to retrieve intact during reconnaissance. Treat it as evidence
that QPN is widely submitted rather than an exact prevalence.

**Partially answered live, 2026-08-20: units submit QPN rows of zero.** All
four captured Drax rows carry `levelFrom` and `levelTo` of 0, so a QPN row
exists even when there is nothing to deduct. Two consequences:

- Much of the per-period volume above is likely zero rows, so how often QPN is
  *non-zero* — the number that actually moves the shortfall — remains unknown.
  Worth one aggregate query during S1.1 before deciding how loudly the staging
  layer should warn about it.
- Whether *every* unit submits rows, or only some, is still open. A missing row
  meaning "no deduction" versus "unit does not submit QPN" are different things
  in a join, and one unit's behaviour does not settle it.

## Proposed table

Same shape as the `PN` table, same key, because the grain is identical:

```sql
PRIMARY KEY (bm_unit, settlement_date, settlement_period, time_from, retrieved_at)
```

Kept as its own table rather than columns on the `PN` table. The raw layer
records what each source published, and these are two publications that can
arrive at different times and be revised independently. Combining them is a
staging-layer decision.

## One parse function, not two

Identical schema, identical parameters, identical grain. This is the clearest
case in the Elexon set for a single parse function taking the dataset name as an
argument, rather than two near-identical modules.

`MELS` and `MILS` are the other such pair. Whether all four share one
implementation is the design call at the top of S1.1.

## Priority

**Phase 1, first — same session as `PN`.** Not optional. Without it, step 1 of
the thesis measures a shortfall that includes every quiescent MW in the country.
