# PN, Physical Notifications

**Not yet ingested.** Planned for Phase 1.

## In plain terms

**The promise.** Ahead of time, every power station tells the grid operator how
much electricity it intends to produce in each half hour.

It is submitted as points on a line rather than a single number, so a station
ramping up says "I will be at 100 MW at 14:00 and 300 MW at 14:30" rather than
"I will average 200 MW".

Paired with `B1610`, which records what actually came out, this is how you find
generators that fell short of what they said they would do. That shortfall is
the starting point of the whole project.

---

A Physical Notification is a participant's best estimate of what a BM unit will
export or import in a settlement period. It is the commitment side of the
thesis: what a generator said it would do, against which `B1610` records what it
actually did.

## Endpoint

```
GET https://data.elexon.co.uk/bmrs/api/v1/datasets/PN/stream
```

| Parameter | Required | Notes |
|---|---|---|
| `from` | yes | ISO datetime |
| `to` | yes | ISO datetime |
| `settlementPeriodFrom` | no | Untested on this dataset. On BOALF and MELS these switch `from`/`to` to filter on settlement **date** rather than time; on B1610 they had no effect. Verify before using |
| `settlementPeriodTo` | no | As above |
| `bmUnit` | no | Array. Not used in ingestion; pull everything |

No documented maximum range for this endpoint.

## Response

Bare array, no envelope.

```json
[
  {
    "dataset": "PN",
    "settlementDate": "2026-08-01",
    "settlementPeriod": 5,
    "timeFrom": "2026-08-01T01:00:00Z",
    "timeTo": "2026-08-01T01:30:00Z",
    "levelFrom": 0,
    "levelTo": 0,
    "nationalGridBmUnit": "DRAXX-1",
    "bmUnit": "T_DRAXX-1"
  }
]
```

| Field | Type | Notes |
|---|---|---|
| `dataset` | `str` | Always `PN` |
| `settlementDate` | `str` | **Local time date.** See the source README |
| `settlementPeriod` | `int` | 1 to 50 |
| `timeFrom` | `str` | UTC, seconds, `Z` suffix |
| `timeTo` | `str` | UTC |
| `levelFrom` | `int` | MW at `timeFrom` |
| `levelTo` | `int` | MW at `timeTo` |
| `nationalGridBmUnit` | `str` | e.g. `DRAXX-1` |
| `bmUnit` | `str` | e.g. `T_DRAXX-1`. The Elexon identifier |

## PN is a ramp, not a level

`levelFrom` and `levelTo` with `timeFrom` and `timeTo` describe a **straight
line between two points**, not a flat value for the period.

When output is steady, `levelFrom` equals `levelTo` and there is one row per
settlement period. When it changes, a unit can submit several point pairs within
a single period and you get several rows.

**This matters for the comparison against B1610.** B1610 reports metered volume
in MWh for a whole settlement period. PN reports MW at instants. Comparing them
means integrating the PN ramp into a volume first, which is not a straight join.

That integration is a candidate for the settlement period macro at S2.

## Proposed table

Not yet built. The key needs `time_from`, because a unit can have several rows
in one settlement period:

```sql
PRIMARY KEY (bm_unit, settlement_date, settlement_period, time_from, retrieved_at)
```

Worth confirming against real data before committing: find a period where a
unit submitted multiple points and check nothing collides.
